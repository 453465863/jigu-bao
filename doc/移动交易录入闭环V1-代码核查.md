# 移动交易录入闭环 V1：现有代码核查

核查日期：2026-10-01。依据用户提供的《叽咕包移动交易录入闭环 V1》。本文记录现状，不代表 V1 已实现。

## 已有基础

- 支付宝、金太阳等账户可切换；基金、持仓、交易、待处理队列等数据按当前账户隔离。`tmp/account-switch-smoke.cjs` 通过，但它是 store 模拟测试，不覆盖实际手机页面和重启后的全流程。
- 已有场外基金净值、基金确认天数接口和交易日历，可以复用来计算预计日期。
- 已有截图 OCR、基金代码识别和持仓导入入口，以及手动买卖、补录当前持仓入口。

## 与 V1 不一致的地方

| 要求 | 当前实现 | 必须补的能力 |
| --- | --- | --- |
| 截图作为交易主入口 | `useScanImport` 主要识别基金代码、持仓金额和收益，直接换算持仓 | 截图类型识别、字段草稿、手机全屏确认，确认前不记账 |
| 场内 ETF 成交 | `TradeModal` 和 `useHoldingProfit` 仍按基金净值处理 | 成交价、份额、时间、费用、现金、已实现收益；行情用场内价格 |
| 场外申购三段状态 | 只有以净值为基础的待处理队列；交易记录只有一个 `date` | 申请、等待确认、实际确认；预计与实际日期分别保存 |
| 现金及待确认资产 | `targetAllocationPlanner.cash` 是规划页面的手动数字，交易不自动更新 | 账户级现金账本及待确认申购余额；确认时不可二次扣现金 |
| 确认截图匹配 | 没有确认截图交易匹配 | 更新原申购记录，多笔候选必须让用户选择 |
| 去重 | 待处理队列按 ID 去重 | 截图 SHA-256、交易语义相似检测和人工确认 |
| 账户冲突提醒 | 当前账户控制存储路由；截图尚不识别平台 | 平台只用于提醒，不能选择或切换写入账户 |

## 开发顺序建议

1. 先把账户级现金、交易草稿、交易状态和幂等写入规则设计清楚，同时明确旧数据兼容方式。第一阶段只做手动场内成交、场外申购和补录持仓分流；每一步验收后暂停。
2. 场内 ETF 行情价格与手动成交同阶段处理，至少先禁止把 NAV 当场内价显示收益。否则手动交易验收仍会出现错误盈亏。
3. 做手机全屏截图确认页，先用固定识别草稿验证页面、账户锁定和字段校验，不写账本。
4. 接交易状态机、现金和持仓原子更新，验证重复提交、确认截图匹配和账户隔离。
5. 接多模态截图识别，再使用真实金太阳和支付宝截图做端到端验收。真实截图验收必须安排在识别接入之后。

- 相关组件、store、账户模块、截图及持仓计算模块 ESLint：0 错误，10 个既有 React Hook/Compiler 警告。

## 第一批代码落地状态（2026-10-02）

- 新增 `app/lib/trading/`：场内成交、场外申购/确认、统一提交、预计日期和待确认金额计算。适配现有按代码索引的 `holdings` 数据形状。
- 新增 `/trade-entry/` 手机全屏录入页：当前头像账户固定显示；上传截图后人工填写草稿或手动录入；对必填字段、多笔待确认申购和错账户做校验。此批尚无多模态识别。
- 新账本 `tradeJournal` 只写本机、按账户隔离，不在 `SYNC_KEYS`；记录现金、交易和由交易计算出的持仓。为避免旧首页用基金 NAV 计算场内 ETF 错误盈亏，新持仓暂时只在交易录入页显示，尚未并入首页资产。
- 当前本机页不是 V1 最终验收：上传原图已有 SHA-256 去重，但缺少真实截图识别、交易语义去重、ETF 场内行情和首页资产联动。不能拿这页的人工草稿流程声称截图闭环已完成。
- `tmp/trading-flow-smoke.mjs` 覆盖 ETF 买卖、现金与成本、场外申购与确认、重复确认、错账户、多笔匹配；`tmp/account-switch-smoke.cjs` 覆盖新账本本地隔离和不触发云端同步。
