# 基估宝移动交易录入 V1 交接

更新：2026-10-02。本文件供当前任务继续或新任务接手；以实际代码和测试结果为准。

## 目标与约束

- 原项目二次开发，保留现有账户系统和 `storageStore`；手机当前头像账户决定写入账户，截图平台只用于冲突提醒。
- 截图是最终主入口，手动录入是辅助。已新增 `app/lib/trading/recognizeTradeScreenshot.js`，负责将多模态输出规范化为交易草稿；实际多模态服务尚未接入，上传图片后仍须人工填写草稿。
- 用户已在 2026-10-05 明确授权：为实现手机脱离电脑且与电脑使用同一份数据，新账户账本、现金、交易记录与目标计划可同步到用户自己的 Supabase 账户。`accountLedgers` 已加入同步契约；未配置 Supabase 或未登录时仍只保存在本机。
- 分阶段预览验收，勿一次性改完；高 token 工作先列范围。
- 不展开 AI 投资分析、新闻、量化或新行情系统。

## 当前已实现

- `app/lib/trading/`：交易常量、场内 ETF 买卖、场外申购/确认、统一提交、预计日期、待确认金额。现有持仓形状为 `holdings[code] = { share, cost }`。
- `app/trade-entry/page.jsx`：全屏手机录入页，使用 `useStorageStore.activeAccountId` 和现有账户设置；上传原图或手动填写后进入 `ScreenshotConfirm`。
- 交易页现在也可直接粘贴图片：桌面端按 Ctrl+V，或点“粘贴剪贴板图片”。粘贴与选文件共用截图 Hash、预览和人工确认流程；浏览器剪贴板权限及手机系统兼容性仍需实际操作验收。
- 上传原图生成 SHA-256，同一原图重复提交受拦截；多笔相同基金待确认申购要求用户选原交易。
- 交易、现金、派生持仓写在当前账户本机 `tradeJournal`，并在交易页显示；支付宝旧账户使用本地 key，其他账户存于本地 `accountLedgers`。
- 新交易账本从空持仓开始；旧持仓不会自动迁移，当前也不能从新账本卖出旧持仓。迁移须先核对份额和成本，避免重复计入资产。
- 已新增 `app/lib/etfQuote.js`，读取腾讯场内 ETF 报价并拒绝用基金净值冒充场内价；尚未接入首页资产与收益计算。
- `TradeJournalValuation.jsx` 已接入交易页的本机新 ETF 持仓展示；有场内报价才计算市值和浮动盈亏，无报价显示不可用。旧首页仍未联动。
- `ScreenshotConfirm.jsx` 已加入低置信度字段提示和截图平台冲突勾选确认。实际多模态请求仍未接入。
- B/C 小组长首轮静态审查发现的旧申购 ID、负手续费、无效报价日期已修补；交易页也已加账户切换时的草稿与账本归属保护。相关 ESLint、ETF 报价及交易/账户冒烟检查通过；页面交互和真实接口仍待实测。
- 首页相机图标进入 `/trade-entry/`。预览服务地址：`http://localhost:3000/trade-entry/`。

## 已知缺口与下一阶段顺序

1. **静态构建已通过。** `next build --webpack` 退出码 0，生成 `out/index.html` 与 `out/trade-entry.html`。`package.json` 已使用这个构建选项；还需真实浏览器操作验收。
2. **处理账本与首页资产的唯一来源。** 新交易持仓目前仅在 `tradeJournal.holdings` 显示，尚未并入旧首页资产。接入时必须保证同一持仓只计一次，且不得把本机交易数据通过旧 `holdings` 同步链路上传云端。
3. **场内 ETF 行情与收益。** 先检查现有 `app/api/fund.js` 是否有 513300 场内成交价；复用或最小扩展现有 provider。无场内价时显示不可用，绝不回退用 NAV 算场内盈亏。
4. **补齐截图主入口。** 多模态只产草稿，低置信度字段留空；手机确认后才提交。平台冲突提醒、语义去重、支付宝确认截图匹配原申购。需真实金太阳和支付宝截图验收。
5. **账户现金基线。** 当前首次记账需要手工填起始现金；后续应有明确的余额录入/校正记录，避免直接改现金造成无法复盘。

## 用户验收缺陷记录

- 2026-10-06，R9 云端接通验收：用户从首页点击头像并进入“本地设置”时，页面出现“`activeAccountId is not defined`”，关闭提示或重新尝试均无法恢复。期望头像菜单和本地设置正常打开。根因是 `page.jsx` 已向 `UserMenu` 传入当前账户 ID，但 `UserMenu` 的参数列表漏接该属性；已补齐参数，等待按原路径复验。
- 2026-10-06，R9.2 登录验收：用户在电脑和手机打开头像区域时，导航栏下方出现一大片模糊/深色空白区域。期望账户与登录菜单以清晰的小型下拉框显示。第一次仅修改下拉框定位后用户复验仍失败；第二次移除导航栏模糊后仍残留深色空白。第三次定位到移动端仍使用旧版双行导航的 `padding-top: 140px`，已按当前单行 68px 导航改为 80px（含 12px 间距）。构建通过后仍须按用户原路径复验，缺陷在真机复验前保持 OPEN。
- 2026-10-06，R9.3 密码管理：云同步登录弹框已补“忘记密码”，通过 Supabase 发送重置邮件；重置链接返回时监听 `PASSWORD_RECOVERY` 并打开“设置新密码”。已登录用户可从头像菜单进入“修改密码”，注册和改密都要求两次密码一致；原有登出功能保留。相关新增文件 targeted ESLint 通过，生产静态构建通过；真实邮件跳转须在公开网址配置后验收。
- 2026-10-06，R9.3 用户复验发现：页面缩放或小视口下登录弹框无法滚到底，且注册明确返回 Supabase 仍要求确认邮箱。弹框滚动修复为 overlay 与 modal 均可纵向滚动，短内容继续居中，长内容从顶部开始并保留安全区；注册失败须在 Supabase Email provider 中关闭 `Confirm email` 后复验。
- 2026-10-07，R9.4 跨设备同步用户验收失败：电脑和手机均可登录，但手机仍显示初始数据。定位到旧同步策略把第二台设备当作配置冲突，并由数据库 RPC 按 `last_device_id` 拦截。个人多设备模式改为：首次显式登录且云端为空时自动上传当前本地数据；云端已有数据时新设备默认下载；同步调用默认允许设备接管，避免手机与电脑互相阻断。仍需用电脑重新上传正确数据，再在手机重新登录验证。

## 登录与本地模式决策

- 当前为个人使用产品，默认允许免登录本地使用。账户、资产、交易录入和目标配置不以 Supabase 登录为前置条件。
- Supabase 登录仅用于用户主动开启的手机/电脑云同步；头像菜单保留“登录并开启云同步”。登录弹框必须提供“继续免登录使用”。
- Supabase 免费默认邮件服务不允许编辑 Magic Link/OTP 模板，用户不为个人项目额外配置 SMTP。登录改为邮箱和密码；关闭 Supabase 的 Confirm email 后，无需邮件网页跳转。免登录仍为默认可用路径。
